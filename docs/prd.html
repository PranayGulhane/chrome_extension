Product Requirements Draft v0.1

LinkedIn Job Outreach Assistant
Chrome Extension

A lightweight Chrome extension backed by a full FastAPI + CockroachDB platform. The extension sits on LinkedIn, lets users select hiring posts, and uses AI agents to draft and send personalized cold emails — all in under 60 seconds.

AuthorPranay Gulhane
Last Updated1 July 2026
Target ReleaseQ3 2026
PlatformChrome MV3 + FastAPI
RolesAdmin · JobSeeker
01

Overview

Job seekers routinely scroll LinkedIn searching for hiring posts — typically filtered to the last 7 days — and then manually identify the recruiter, extract the job description, compose a cold email, and track whether they sent it. This process is slow, inconsistent, and impossible to scale.

This product is a Chrome extension that functions as the user-facing layer of a full-stack job outreach platform. A keyboard shortcut opens a floating panel directly on LinkedIn. The user clicks a hiring post; AI agents extract the poster's details, parse the JD, and draft a tailored cold email using the user's saved profile and resume context. One more click sends it via the user's own Gmail account.

Every application is saved to a central database. The platform supports multiple user profiles scoped to different target job titles, a resume PDF parser to auto-populate profiles, and an admin dashboard for usage and billing metrics across all accounts.

02

Problem Statement

The current job application workflow on LinkedIn is broken at every step:

  • Discovery is manual. Users search for posts like "genai + hiring", scroll through noise, and read each post individually to find relevant opportunities.
  • Extraction is tedious. Getting the poster's name, profile URL, email (buried in the post text), and job description requires careful reading and copy-paste.
  • Cold emails are generic. Without tooling, users write the same email repeatedly or use low-quality templates that don't reference the specific JD.
  • Tracking is non-existent. Most people have no record of what they applied to, when, or what email they sent.
  • Context switching is constant. Copying from LinkedIn → writing in Gmail → tracking in a spreadsheet → returning to LinkedIn takes 10–15 minutes per application.

Goals & Non-Goals

Goals — v1

G1Floating extension panel activated by a 2-key shortcut (Alt+J) directly on LinkedIn — no tab switching.
G2One-click post extraction of poster name, LinkedIn profile URL, and full post content from any LinkedIn hiring post.
G3AI email drafting — agents parse the JD from the post and generate a tailored cold email using the user's active profile.
G4One-click send via the user's own Gmail account using OAuth2 — no third-party email service.
G5Auto-save every application to CockroachDB regardless of whether the user sends the email.
G6Rich user profiles with all personal, professional, education, and skill details — multiple profiles per user, each scoped to a target job title.
G7Resume PDF parser to auto-populate a profile from an uploaded resume, with manual correction available.
G8Admin metrics dashboard — per-user token consumption, applications sent, and usage data for billing without exposing private profile details.

Non-Goals — v1

No support for job boards other than LinkedIn in v1 (Naukri, Indeed deferred).
No automated bulk outreach — user must select each post individually.
No LinkedIn API usage — extension reads DOM only; no official LinkedIn integration.
No AI-based job matching or recommendation — user searches LinkedIn themselves.
No mobile browser support.
No Outlook / non-Gmail email sending in v1.

Core Workflow

This is the primary end-to-end user journey — from LinkedIn search to sent email in under 60 seconds.

1

Search & Filter on LinkedIn

User searches for a hiring-related query (e.g., genai hiring) on LinkedIn, opens the Posts section, and filters to "Past week". Extension is inactive — toolbar icon is grey.

2

Activate the Floating Panel

User presses Alt+J. A floating side panel slides in from the right side of the page, overlaid on LinkedIn. The panel shows the active profile selector and an instruction to click a post. Pressing Esc closes it.

→ Extension enters selection mode. Hiring posts are highlighted on hover.
3

Select a Hiring Post

User clicks anywhere on a post card. The content script captures the full post DOM and sends it to the backend. The panel shows a loading state ("Analysing post…").

→ Extracted: poster name, LinkedIn profile URL, full post text, post timestamp.
4

AI Agents Parse the Post

Backend runs two agents in sequence: JD Parser extracts job title, company, required skills, seniority, and email address from the post content. If an email is found, it flows to the next step automatically. If not, the user is shown the extracted details and prompted to enter the recipient email manually.

Email found → Auto-proceed to draft. No email → Manual entry prompt.
5

Select Profile & Draft Email

User selects which of their saved profiles to use (defaults to the last-used one). The Email Drafter agent generates a personalized cold email: subject line + body, using the parsed JD and the user's profile context (headline, skills, experience summary, relevant projects). The draft appears in the panel — fully editable before sending.

6

Review & Send

User reads the draft, edits if needed, and clicks Send. The backend builds a multipart email: the drafted text body + the active resume PDF for the selected profile attached automatically. The resume sent is always the one marked active on the profile in use — not a generic resume. The backend calls Gmail API and sends from the user's own Gmail address.

→ Email + profile-specific resume PDF sent from user's Gmail. → If no resume is uploaded for the active profile, user is warned before sending.
7

Auto-Save Application Record

Regardless of whether the user clicks Send, the application record is saved to the DB at step 4 (post extracted). On send, the record is updated with the final email body, sent timestamp, and status: sent. The panel shows a link to the application in the tracker.

08

AI Agent Pipeline

Four agents power the backend. All LLM calls are logged to agent_usage_logs for per-user token accounting. Each agent lives in its own module under backend/agents/.

Dependency hygiene: Agent orchestration is built on LangGraph (open source, actively maintained) using its StateGraph / functional API with Pydantic v2 structured outputs for every agent's IO. Do not use LangChain's legacy initialize_agent, LLMChain, or AgentExecutor helpers — deprecated since LangChain 0.1/0.2 and limited to critical fixes only. Groq model IDs must be re-checked against console.groq.com/docs/deprecations before every release — Groq retired multiple models in 2026 (e.g. llama-3.3-70b-versatile, llama-3.1-8b-instant) with short notice, so model IDs should be a config value, not hardcoded in agent code.

A1v1

JD Parser

Reads raw post text and extracts structured job data. Identifies hiring intent. Parses email addresses using regex + LLM verification.

IN Post text (string) OUT job_title, company, email, skills[], seniority, location, is_hiring
A2v1

Email Drafter

Generates a personalized cold email. Uses parsed JD + user profile context (headline, skills, experience summary, relevant projects). Targets brevity — 150–200 words.

IN parsed_jd, user_profile, active_resume_context OUT subject (string), body (string)
A3v1

Resume Parser

Extracts text from an uploaded resume PDF (via pdfplumber, fallback pypdf), then uses an LLM to map content to the profile schema. User can review and correct any misparse.

IN resume_text (extracted from PDF) OUT partial UserProfile object (all parseable fields)
A4v2

Post Relevance Scorer

Scores a post for relevance against the user's active profile. Helps user prioritize which posts to apply to. Displayed as a match percentage in the panel.

IN parsed_jd, user_profile OUT score (0–100), reasoning (string)

Token logging is mandatory on every agent call. Log: user_id, agent_name, model_used, input_tokens, output_tokens, latency_ms, timestamp. This powers both user-facing usage displays and admin billing metrics.

09

Gmail Integration

Emails are sent from the user's own Gmail account. The platform never stores or proxies email credentials — it uses a standard Google OAuth2 flow with the minimum required scopes.

OAuth2 Flow

1

User connects Gmail

From the Options page or first-time setup, user clicks "Connect Gmail". Backend initiates a Google OAuth2 PKCE authorization code flow with scope https://www.googleapis.com/auth/gmail.send only.

2

Token storage

After consent, the backend exchanges the code for an access token + refresh token. Both are stored encrypted in the gmail_credentials table (access token encrypted at rest). The user's Gmail address is stored for display only.

3

Sending an email with resume attachment

When the user clicks Send, the backend: (1) retrieves and decrypts the access token, (2) fetches the active resume PDF for the user's selected profile from storage, (3) builds a multipart/mixed MIME message with the email body as text/plain + text/html and the resume as a application/pdf attachment, (4) base64url-encodes the full message and calls gmail.users.messages.send. The attachment filename is set to {FirstName}_{LastName}_{TargetJobTitle}_Resume.pdf.

No active resume on the profile → send is blocked with a prompt to upload one first.
4

Token refresh

If the access token has expired, the backend automatically refreshes it using the stored refresh token before sending. The updated access token is re-encrypted and saved back.

Security note: Gmail scope must be limited to gmail.send only — not gmail.readonly or broader. Users can revoke access at any time from Google Account settings. A "Disconnect Gmail" option is available in the extension Options page.

Resume Management & Parser

The resume PDF uploaded to a profile serves two purposes: (1) it is parsed by agent A3 to auto-populate the profile fields, and (2) it is the file attached to every email sent from that profile. Only the resume for the active profile is attached — never a resume from a different profile.

Upload & Parsing Flow

  • Upload flow: User picks a target job title first, then uploads the PDF. This scopes the parsing context so the agent can make better inferences.
  • Parsing: Backend extracts text with pdfplumber (fallback: pypdf), sends it to Resume Parser agent (A3), and returns a pre-filled profile form. All parsed fields are editable before saving. PyMuPDF is intentionally excluded — it is AGPL-3.0 licensed, which is incompatible with closed-source distribution.
  • Error handling: If a field is missing or ambiguous, it is left blank rather than hallucinated. The UI highlights unpopulated required fields.
  • Re-upload: User can upload a new version at any time. The new upload becomes the active resume for that profile. Previous versions are retained in resume_uploads with is_active = false so re-parsing history is auditable.

Resume as Email Attachment

  • Profile-scoped: Each profile has its own active resume. User with three profiles (GenAI Engineer, Data Engineer, Software Engineer) has three separate resumes. The correct one is selected automatically at send time based on which profile the user chose for the application.
  • Filename convention: When attached, the file is renamed to {FirstName}_{LastName}_{TargetJobTitle}_Resume.pdf (e.g., Pranay_Gulhane_GenAI_Engineer_Resume.pdf) regardless of the original upload filename.
  • No resume guard: If the active profile has no uploaded resume, the Send button is disabled and a prompt is shown: "Upload a resume for this profile before sending."
  • Storage: PDF files are stored in object storage (S3-compatible). The backend reads the file at send time by path — it is never returned to the browser/extension client.

User Stories

As a job seeker on LinkedIn, I want to press a shortcut key and click a hiring post so that I can get a drafted cold email in under 10 seconds without leaving LinkedIn.
As a user targeting multiple roles, I want to save a separate profile for each job title (e.g., "GenAI Engineer" and "Data Engineer") so the email drafts are tailored to the specific role I'm applying for.
As a user setting up my profile, I want to upload my resume PDF and have the system auto-fill my profile fields so I don't have to type everything from scratch — and I can correct anything the parser got wrong.
As a user composing an email, I want to edit the AI-drafted email before sending so I can personalize the tone or add context the AI missed.
As a user connecting Gmail, I want to authorize the extension to send emails from my Gmail account using a standard Google sign-in flow so I never have to share my password with the app.
As a user reviewing past applications, I want to see every post I clicked — with the email I sent and its current status — so I can track my outreach and follow up when needed.
As Pranay (admin), I want to see how many tokens each user consumed today so I can track LLM costs and plan billing without seeing users' private data.
As a user on a post with no email address, I want the extension to tell me no email was found and let me enter one manually, so I can still use the drafting and tracking features.

Open Questions

All open questions are resolved below. No remaining blockers before implementation.

✓

LLM provider — Groq. All agents (JD Parser, Email Drafter, Resume Parser) use Groq's inference API. Recommended models: llama-3.3-70b-versatile for drafting quality, llama-3.1-8b-instant for fast parsing tasks. Groq's low-latency inference is critical for hitting the <3s draft target. Token accounting in agent_usage_logs uses Groq's reported usage.prompt_tokens and usage.completion_tokens from the API response. The model_used field on each log row captures the exact model string.

✓

"See more" — attempt programmatic expansion; fall back to user prompt. LinkedIn truncates long posts behind a "…see more" clickable span. Programmatically clicking a visible DOM button (simulating a user tap) is not bulk scraping and does not violate LinkedIn's policies — it is equivalent to the user clicking it manually. Resolution: when the user selects a post in selection mode, the content script checks if a "see more" element is present and unexpanded. If found, it programmatically clicks it and waits up to 800ms for the DOM to update before reading the full text. If programmatic expansion is blocked or fails (LinkedIn changes the element, click is intercepted, or expansion doesn't complete in time), the panel shows a non-blocking inline prompt: "This post looks truncated — click '…see more' on the post to expand it, then click the post again." The user expands it manually and re-selects. No capture proceeds on truncated content; a flag in the application record (was_truncated: bool) marks cases where only partial text was captured.

✓

No-email fallback — outreach type selection with DB note. When the JD Parser finds no email in the post, the panel prompts the user to indicate how the poster asked to be contacted. The user selects one of four outreach types, which is saved to the application record:

emailPoster included an email — user enters it manually. Full draft + send flow proceeds normally.
linkedin_dmPoster said "DM me". Extension saves the record with the poster's LinkedIn URL as the outreach target. AI drafts a DM-length message (copied to clipboard) instead of an email.
apply_via_linkPost contains a job application URL. User pastes the URL into the panel. Saved as outreach_note. No email drafted — record saved for tracking purposes.
reach_out_otherPoster directed to a different person (e.g., "contact @Jane"). User enters the person's name or URL. Saved as outreach_note. User handles that outreach manually.

All four types save a full application record with outreach_type and outreach_note fields. The tracker displays the outreach type as a visible tag so the user knows at a glance how to follow up on each saved application.

✓

Resume storage — Cloudflare R2. PDFs are stored in Cloudflare R2 object storage. R2 is S3-compatible (works with boto3 using a custom endpoint URL — no code changes from standard S3 usage), has a generous free tier (10 GB storage, 1M Class B ops/month free), and charges zero egress fees — important since the backend reads the PDF on every email send. File path convention: resumes/{user_id}/{profile_id}/{upload_id}.pdf. Presigned URLs are never exposed to the client — the backend reads the file server-side at send time only.

✓

Access model — invite-only, no billing in v1. The extension is not publicly available. New users require an invite code generated by the admin. Signup flow: user enters email + password + invite code; backend validates the code (single-use, stored in an invite_codes table) before creating the account. The admin dashboard shows invite code usage. No payment, no subscription, no usage limits in v1. Token tracking is kept in place so billing can be added in v2 without a schema change.

✓

LinkedIn ToS — resolved via safe content script architecture. The extension is compliant by design: the content script only reads the DOM of a post the user has manually selected. It never touches social metadata, feed noise, or LinkedIn's internal APIs.
